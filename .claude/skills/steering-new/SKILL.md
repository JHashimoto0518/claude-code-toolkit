あなたはこのリポジトリの `CLAUDE.md` に定義されたステアリング運用に従って、新しい作業単位のドキュメントを作成します。

引数: `$ARGUMENTS`
(開発タイトルとして扱う。ユーザー自身が指定したものであり、何を作るのかを内容から推測し直さない。誤字や句読点などの体裁は手順2の範囲で整えてよい。日本語で指定された場合のみ、ディレクトリ名にする際に英語の kebab-case へ翻訳する。既に英語 kebab-case 相当であればそのまま使う)

## 手順

1. **ディレクトリ作成**
   - `$ARGUMENTS` が空の場合、開発タイトルをユーザーに質問してから開始する(日本語・英語どちらでもよい旨を伝える)。
   - 開発タイトルが日本語の場合は英語の kebab-case に翻訳し、ディレクトリ名に使う(例: 「タグ機能の追加」→ `add-tag-feature`)。既存の `.steering/*` のタイトルと同程度の粒度・命名感に合わせる。既に英語 kebab-case であればそのまま使う。
   - 今日の日付を `YYYYMMDD` 形式で取得し、`.steering/[YYYYMMDD]-[NN]-[開発タイトル]/` を作成する(例: `.steering/20250115-01-add-tag-feature/`)。
   - `NN` は**同日内の連番**(`01` から始まる 2 桁のゼロ埋め)。同じ日付で始まるディレクトリの件数 + 1 を使う。同日に既存がなければ `01`。件数は次で確認する(`20250115` は今日の日付に読み替える)。

     ```bash
     ls -1 .steering/ | grep -c '^20250115-'
     ```

     - 連番を付ける理由: 日付だけだと同日に複数作成したときディレクトリ名のソート順が作成順と一致せず、経緯を追う際に前後関係を誤読する。
     - 連番のない旧形式(`[YYYYMMDD]-[開発タイトル]`)のディレクトリが残っているリポジトリでは、過去分をリネームしない(過去のコミットタイトルが旧名を埋め込んでおり、リネームすると対応が失われるため)。同日に旧形式がある場合もそれを件数に含めて次の番号を決める。
   - 既に同名ディレクトリが存在する場合は、上書きせずユーザーに確認する。

2. **overview.md の作成(背景・要求の概要)**
   - 作成したディレクトリに `overview.md` を作成する。H1 見出しには `$ARGUMENTS` で指定された開発タイトルを、**文書の見出しとして読める体裁に整えて**入れる。`## 目的` 以降は次の軽量なテンプレートのみとし、具体的な内容はまだ埋めない(ユーザー自身が後で編集するため):
     ```markdown
     # [開発タイトル]

     ## 目的

     (ここに背景・要求の概要を記載してください)

     ## 注意事項

     (制約条件や注意点があれば記載してください)
     ```
   - H1 に入れるのは日本語なら日本語のままであり、ディレクトリ名用の英語 kebab-case ではない(例: ディレクトリが `20250115-01-add-tag-feature/` でも、H1 は日本語で書く)。
   - **整えてよいもの**(気づいたら直す):
     - 誤字・脱字・変換ミス
     - 不適切または不足している句読点、読みにくい語順
     - リポジトリ内の正式表記との不一致(識別子・関数名・ファイル名などはコード上の正確な表記に合わせる)
     - 見出しとして必要な用語の補完(例: 「`notify_user` を呼び出したい」→「`notify_user` 関数を呼び出す」)
     - 依頼口調の語尾(「〜したい」「〜してほしい」)を、見出しらしい体言止め・断定形へ調整する
   - **変えてはいけないもの**:
     - 開発の意図・目的・対象スコープ。言い回しの調整に留め、別の要求に読み替えない
     - ユーザーが明示した情報の削除。短くするために要素を落とさない
     - 指定されていない前提・手段の追加(「非同期で」「バッチで」など、ユーザーが書いていない実現方法を勝手に足さない)
   - 判断に迷う場合はユーザーの指定表現を尊重する。原文から大きく変えた場合は、H1 をどう整えたかを作成報告時に一言添え、ユーザーが直せるようにする。
   - 作成後、ユーザーに「`overview.md` に背景・要求の概要を記入し、書き終えたら進めるよう指示してください」と伝え、**指示があるまで次のステップ(requirements.md の作成)に進まない**。ユーザーが無言で他の話題に移った場合は進めるべきか確認する。
   - ユーザーから進める指示があったら、その時点の `overview.md` の内容を読み込み、以降のステップの「背景・要求の概要」として扱う。

3. **requirements.md の作成**(overview.md 記入後、ユーザーの進行指示を受けてから)
   - `overview.md` の内容を読解した上で作成する(`overview.md` の文面をそのまま複製・引用するのではなく、通常どおり読解して反映する)。
   - 既存の `.steering/*/requirements.md` の構成(背景 / 変更・追加する機能の説明 / 受け入れ条件 / 制約事項)に倣う。
   - **H1 の直後に `## 要点` を置く**(後述の「「要点」セクション」を参照)。ここには「何をどう変えるか」と「今の方式のどこを捨てるか」を書く。
   - 背景セクションは、必要に応じて過去のステアリングディレクトリ(`../[既存ディレクトリ]/`)への相対リンクで経緯を示す。
   - 作成後、**内容をユーザーに提示し、承認を得るまで次に進まない**。

4. **design.md の作成**(requirements.md 承認後)
   - 既存の `.steering/*/design.md` の構成(実装アプローチ / 変更するコンポーネント / データ構造の変更 / 影響範囲の分析)に倣う。
   - **H1 の直後に `## 要点` を置く**(後述の「「要点」セクション」を参照)。ここには「どの方式を採るか」と「それを分けた決め手」を書く。
   - 「影響範囲の分析」には後方互換性への影響を含める。配慮の要否はリポジトリのバージョニング方針に従う(`CLAUDE.md` の「バージョニングと後方互換性ポリシー」を参照)。本番未リリースであれば、壊す変更を自由に行ってよい。
   - 作成後、**内容をユーザーに提示し、承認を得るまで次に進まない**。

5. **永続的ドキュメント(`docs/`)の更新**(design.md 承認後、tasklist.md 作成前)
   - design.md の内容をもとに、`docs/` 配下(`architecture.md` / `functional-design.md` / `product-requirements.md` など)・`README.md`・各種 `*_GUIDE.md` のうち影響を受ける箇所を特定する。
   - 影響がある場合: 該当ファイルを実装より先に更新し、変更内容(diff相当)をユーザーに提示する。**承認を得るまで次に進まない**(tasklist.md の作成・実装のいずれも開始しない)。
   - 影響がない場合: その旨を明示し、次のステップに進む(この場合は承認待ちにしない)。
   - **この段階では実装ファイル(アプリケーションコード・インフラ定義など)を一切変更しない。** ドキュメント更新と実装を同一ステップで進めない。

6. **tasklist.md の作成**(docs更新の承認後、または docs更新不要と判断した後)
   - 既存の `.steering/*/tasklist.md` の構成(実装 / インフラ / テスト / ドキュメント更新 / 未実施・検証待ち、など該当するセクションのみ)に倣い、チェックボックス形式(`- [ ]`)で列挙する。
   - `docs/` 更新は手順5で完了済みのため、tasklist.md の「ドキュメント更新」セクションには steering ディレクトリ内の記録のみを残すか、完了済みとして扱う(未着手のタスクとして再掲しない)。
   - 実環境へのデプロイなど、このセッションで検証できない項目は「未実施・検証待ち」として明示する。
   - **このファイルは承認待ちにしない。** 作成した内容を簡潔に提示し、そのまま手順7の実装に進む。

7. **実装**(tasklist.md 作成後、承認を待たずに着手する)
   - `.steering/[YYYYMMDD]-[NN]-[開発タイトル]/tasklist.md` を今後の実装のタスクリストとして扱う旨を伝えてから着手する。
   - 実装は tasklist.md の範囲に限る。design.md で決めた内容を超える変更が必要になった場合は、その場で進めず一度ユーザーに報告する。
   - 完了した項目は tasklist.md のチェックボックスを `- [x]` に更新する。このセッションで検証できない項目は `- [ ]` のまま「未実施・検証待ち」に残す。

## 「要点」セクション

`requirements.md` と `design.md` は、H1 の直後に `## 要点` を置く。本文を最後まで読まなくても**その文書で何が決まったのかが分かる**ようにするためのもの。

- **位置**: H1 の直後。「背景」「実装アプローチ」など他のどのセクションよりも前に置く
- **対象**: `requirements.md` と `design.md` のみ。`overview.md` は要求そのものが短くユーザーが書くため、`tasklist.md` はチェックリスト自体が要約になっているため、いずれも置かない
- **内容**: 結論を先に書く。requirements なら「何をどう変えるか」と「今の方式のどこを捨てるか」、design なら「どの方式を採るか」と「それを分けた決め手」。採らなかった選択肢がある場合は、その理由を 1 行添える
- **分量**: 数段落、または短い `###` 見出しで区切った数ブロック。スクロールせずに読み切れる範囲に収める
- **書き方**:
  - 判断とその決め手だけを書く。本文の各セクションを順に要約した目次にしない
  - 仕様の対応関係(カラムと意味、担い手と理由など)が中心になる場合は表を使う。散文で並べるより短く済む
  - 本文と内容が重なることを避けなくてよい。要点は本文の抜粋ではなく、本文を読む前提として先に渡す結論である
- 書き方に迷ったら、そのリポジトリの `.steering/` にある直近の `requirements.md` / `design.md` を参考にする。

## 実装開始の条件

- docs更新の承認(手順5)を得ており、かつ tasklist.md(手順6)を作成済みであること。この 2 つが満たされていれば、アプリケーションコードやインフラ定義などの実装ファイルに着手してよい。
- tasklist.md 自体の承認は不要。手順5までの段階承認で設計は確定しており、tasklist.md はそれを作業単位に分解した記録に過ぎないため、ここで承認を挟む意味がない。

## 注意事項

- このコマンドが呼ばれた時点でステアリングドキュメントの作成要否はユーザーが判断済みである。作成するかどうかを自分で判断し直したり、ユーザーに確認したりしない。
- requirements.md / design.md をまとめて一度に提示しない。1ファイルごとに作成し、承認を得てから次のファイル作成に進む。
- requirements.md / design.md には必ず `## 要点` を置く。分量が少ないという理由で省略しない(短い文書ほど要点も短くなるだけ)。
- **ステップの順序は ディレクトリ作成 → overview.md → requirements → design → docs更新 → tasklist → 実装 で固定する。** docs更新を実装完了後や tasklist.md 作成後に後回しにしない。
- 承認が必要なステップは overview.md 記入後の進行指示・requirements.md・design.md・docs更新の 4 つ。これらは明示的な指示・承認の返答を得るまで次のステップの作業に着手しない。ユーザーが無言で他の話題に移った、または内容に触れず先の作業を促しただけの場合は承認とみなさず、意思を確認する。
- tasklist.md は承認ステップではない。作成したらそのまま実装に進む。
- 開発タイトルは `$ARGUMENTS` としてユーザー自身が指定する。何を作るのかを内容から推測し直したり、別のスコープに要約し直したりしない。ディレクトリ名には英語 kebab-case へ翻訳した形を、`overview.md` の H1 には日本語のまま体裁を整えた形を使う(手順2を参照)。
- 背景・要求の概要(`## 目的` 以降)は `overview.md` にユーザー自身が記入する。Claude がこの内容を代わりに書いたり、推測で埋めたりしない(手順2で作成するのは H1 のタイトルとテンプレートのみ)。
  - H1 のタイトルは、ユーザーが指定した内容の体裁を整えて置くだけであり「Claude が内容を書く」ことには当たらない。整えてよい範囲は手順2の定義に従い、`## 目的` 以降を先回りして埋めないこと。
- ユーザーから進める指示があるまで、`overview.md` 作成後は待機する。指示を受けたら、その時点の `overview.md` の中身を読み込んでから requirements.md の作成に進む。
