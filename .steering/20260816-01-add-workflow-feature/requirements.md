# ワークフロー機能の追加

## 要点

**steering-new スキルの手順(承認ゲートの有無・作成するドキュメント)を、`SKILL.md` 本文の自然言語ではなく YAML のワークフロー定義ファイルから読み込む形に変える。** スキル呼び出し時にワークフローを指定すると、その定義に従って手順・承認ゲートが変化する。今回捨てるのは「単一の『通常の開発』ワークフローのみを `SKILL.md` 本文に自然言語でハードコードしている」現状の構造であり、複数ワークフローを外部データとして持てる構造に置き換える。

## 背景

steering-new スキルは現状、ディレクトリ作成 → overview → requirements → design → docs 更新 → tasklist → 実装という単一の承認ゲート付きワークフローのみを、`SKILL.md` 本文の自然言語で定義している(現行の [`steering-new/SKILL.md`](../../plugins/core/skills/steering-new/SKILL.md) 参照)。

一方で実際の開発の性質は多様であり、下記 4 種の運用が既に存在し、今後も増える見込みである。

| ワークフロー | 内容 |
|---|---|
| 通常の開発 | ステアリングのドキュメント・永続化ドキュメントへの反映・実装のすべてに承認ゲートを設ける(現行の steering-new スキルの挙動) |
| 軽微な修正 | 承認を挟まず一度に実施し、最後にユーザーがまとめてレビューする |
| 探索的な開発 | Claude と壁打ちし、結果を overview.md にまとめる |
| 調査 | 調査結果をまとめてドキュメント化する |

これらをすべて自然言語で `SKILL.md` に書き足していくと、条件分岐が複雑化し可読性・保守性が低下する。ワークフローを YAML などのコードとして外部定義できれば、新しいワークフローの追加や既存ワークフローの調整を `SKILL.md` 本文の書き換えなしに行えるようになる。

## 変更・追加する機能の説明

### 1. ワークフロー定義ファイル(YAML)

steering-new スキルの動作(手順の並び、各手順で作成するドキュメント、承認ゲートの有無など)を YAML 形式の外部ファイルとして定義できるようにする。具体的なスキーマ(フィールド名・粒度)は design.md で決定する。

### 2. ワークフロー指定によるスキル挙動の切り替え

steering-new スキル呼び出し時にワークフローを指定できるようにし、指定されたワークフロー定義に従って手順・承認ゲートが変化するようにする。指定がない場合のデフォルト挙動は design.md で決定する。

### 3. 既存 4 種のワークフローの定義化

背景に挙げた「通常の開発」「軽微な修正」「探索的な開発」「調査」の 4 種を、上記の定義ファイル形式で表現する。

## 受け入れ条件

- [ ] ワークフローの手順・承認ゲートが YAML 形式の外部ファイルで定義されている
- [ ] steering-new スキル呼び出し時にワークフローを指定すると、その定義に従って手順・承認ゲートが変化する
- [ ] 「通常の開発」「軽微な修正」「探索的な開発」「調査」の 4 種のワークフローが定義済みである
- [ ] ワークフロー定義を追加・変更する際、`SKILL.md` 本文(自然言語部分)の書き換えが不要である

## 制約事項

- ワークフロー定義言語のフォーマットは YAML とする
- 対象は steering-new スキルの挙動定義に限る。他スキル(core:commit など)への適用は本ステアリングのスコープ外
