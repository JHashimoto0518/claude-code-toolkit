# ステアリングディレクトリの日付が日本時間とずれている

## 要点

**ホストの `/etc/localtime` を読み取り専用でコンテナへバインドマウントし、コンテナのタイムゾーンをホストに追従させる。** `steering-new` スキル(`.claude/skills/steering-new/SKILL.md`)側は変更しない。`date +%Y%m%d` はシステムのローカルタイムゾーンをそのまま使うコマンドであり、コンテナ側のタイムゾーンが正しくなれば、スキルを変更しなくても現地日付を返すようになるため。

| 論点 | 方式 | 決め手 |
|---|---|---|
| タイムゾーンの取得方法 | ホストの `/etc/localtime` を read-only マウント | 追加の設定値なしにホストの実際のタイムゾーンをそのまま反映できる。特定ゾーンのハードコードを避けられる |
| マウント対象ファイル | `/etc/localtime` のみ(`/etc/timezone` は含めない) | `date` の出力補正に必要なのは `/etc/localtime` だけ。`/etc/timezone` はディストリビューションによって存在しないことがあり、含めるとマウント元不在でコンテナ作成が失敗するリスクが増えるだけ |
| `steering-new` スキルの変更要否 | 変更しない | `date` コマンドはシステムのローカルタイムゾーンをそのまま使う。コンテナ側の前提を直せば自動的に解決する |

### 採らなかった選択肢

- **`containerEnv` に `TZ=Asia/Tokyo` などを固定値で設定する** — ホストが日本時間以外のユーザーで同じ問題が再発する。requirements.md の方針(決め打ちを避ける)に反する
- **`containerEnv` に `TZ=${localEnv:TZ}` を設定する** — 多くの Linux/macOS 環境はタイムゾーンを `/etc/localtime` で表現しており、シェルの `$TZ` 環境変数を明示的に設定していないホストでは何も解決しない。`/etc/localtime` マウントで十分なため採らない
- **`steering-new` スキル側で `TZ=Asia/Tokyo date +%Y%m%d` のようにコマンド内で固定する** — コンテナ側ではなくスキル側に決め打ちを持ち込むだけで、根本原因(コンテナが UTC 固定)を放置することになる

## 実装アプローチ

### 1. `.devcontainer/devcontainer.json` へのマウント追加

`.devcontainer/**` は Claude が直接編集できないため、`.steering/20260811-01-fix-steering-directory-date-timezone/proposed/devcontainer.json` に変更後の全文を作成し、ユーザーに適用を依頼する。

```json
"mounts": [
  "source=/etc/localtime,target=/etc/localtime,type=bind,readonly"
]
```

この方式が Windows / macOS / Linux のいずれのホストでも機能する理由: Docker のバインドマウントは「Docker デーモンが動作している OS」上のパスを対象にする。Docker Desktop(Windows / macOS)はいずれも Linux ベースの軽量 VM 上でデーモンを動かしており、その VM は常に `/etc/localtime` を持つ。ネイティブ Linux(このコンテナが動く WSL2 を含む)でも同様。したがって「ホストの実 OS が Windows か Linux か」に関わらず、参照先は常に存在する Linux 上のパスになる。

### 2. `steering-new` スキルの確認

`.claude/skills/steering-new/SKILL.md` の手順1(ディレクトリ作成)が使う `date +%Y%m%d` は、システムのローカルタイムゾーン設定をそのまま反映するコマンドである。コンテナのタイムゾーンがホストに追従すれば、このコマンド自体を変更しなくても現地日付を返す。**スキル側の変更は行わない**(requirements.md の受け入れ条件にある「変更が不要かどうかの確認」の結論)。

## 影響範囲の分析

### 動作への影響

- **`steering-new` のディレクトリ日付**: コンテナ再構築後、ホストの現地日付と一致するようになる
- **Git のコミット日時**: git のコミットタイムスタンプもシステムのローカルタイムゾーンを使って記録される。今回の変更は副次的にコミット日時の UTC オフセット表記も正しくする(この修正の対象範囲そのものではないが、同じ原因を共有する)
- **他のフック・スキル**: `date` コマンドの出力タイミングに依存する処理は `steering-new` の手順1のみで、他への影響はない

### 後方互換性

このリポジトリはまだ正式なバージョニングの対象になっていない。既存の `.steering/2026081*-*` ディレクトリの日付を遡って修正することはしない(過去のコミット履歴にディレクトリ名が刻まれているため)。今回の変更は今後作成されるディレクトリの日付にのみ影響し、移行手順は不要。

### 永続的ドキュメントへの影響

- `docs/` はこのリポジトリに存在しないため、更新対象なし
- `README.md` / `README.en.md` の「使い方」節に、コンテナのタイムゾーンがホストに自動追従する旨(`/etc/localtime` を読み取り専用でマウントすること)を 1 行追記する。利用側リポジトリへ `.devcontainer/` をコピーする際に知っておくべき挙動のため。手順5で具体的な追記内容を提示する
- `claude.md` に本件への直接の言及はなく、更新不要

### 未実施・検証待ちになる見込み

- `.devcontainer/devcontainer.json` の変更はユーザーが適用し、コンテナを再構築しないと反映されない。再構築後に `date` がホストの現地日付を返すことの確認は、このセッション内では完了できない

### 今回の範囲外

- `/etc/localtime` を持たない特殊なホスト環境(Docker デーモン自体が Linux ベースでない特殊な構成など)への対応
- 過去に作成済みの `.steering/` ディレクトリの日付の遡及修正
