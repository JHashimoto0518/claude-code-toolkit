# ステアリングディレクトリの日付が日本時間とずれている

## 要点

原因は `date` コマンドが返す日付そのものではなく、**開発コンテナのシステムタイムゾーンが常に UTC であること**にある。`steering-new` スキルの手順1(ディレクトリ作成)は `date +%Y%m%d` の結果をそのまま `.steering/[YYYYMMDD]-...` の日付に使うため、コンテナが UTC で動く限り、UTC と現地時間の日付がずれる時間帯(日本時間なら 9:00 未満)には前日の日付が使われる。

**コンテナのタイムゾーンを、特定の地域に決め打ちせずホスト環境のタイムゾーンに追従させる。** 「JST に合わせる」対処は採らない。このリポジトリは複数リポジトリで共有する汎用設定であり、[`README.en.md`](../../README.en.md) を持つ時点で日本時間以外のユーザーを想定している。特定タイムゾーンへの決め打ちは、今の「UTC 固定」を「JST 固定」に置き換えるだけで、同じ種類の問題を残す。

## 背景

`steering-new` スキル(`.claude/skills/steering-new/SKILL.md`)の手順1は、ステアリングディレクトリ名の日付部分を次のように取得する。

```bash
date +%Y%m%d
```

このコンテナ(`.devcontainer/devcontainer.json`、ベースイメージ `mcr.microsoft.com/devcontainers/base:bookworm`)はタイムゾーン設定を持たず、`date` は常に UTC を返す。日本時間(UTC+9)のユーザーが 0:00〜8:59 JST の間に作業すると、`date` は前日の日付を返す。実際、本ステアリングディレクトリの作成中にもこの事象が発生した(コンテナの `date` は `2026-08-10`、日本時間は既に `2026-08-11` だった)。

この不一致は `.steering/` のディレクトリ名だけの問題ではなく、コンテナ内で日付を扱う処理全般(コミットのタイムスタンプなど、Git 自体は別途システムクロックの UTC 時刻を正しく記録するため対象外)のうち、**現地日付の意味で `date` を使う箇所**に共通する。

## 変更・追加する機能の説明

### 1. コンテナのタイムゾーンをホスト環境に追従させる

`.devcontainer/` の設定を変更し、コンテナ起動時にホスト環境のタイムゾーンを反映させる。実現方法(ホストの `/etc/localtime` をマウントする、`postCreateCommand` で設定する、など)は design.md で決める。

- 特定のタイムゾーン(`Asia/Tokyo` など)を設定値として決め打ちしない
- ホスト側でタイムゾーンを検出できない、またはこのコンテナの実行環境(WSL2 以外の Docker Desktop など)で同じ手段が使えない場合の扱いも design.md で検討する

### 2. `steering-new` スキル側の対応要否の確認

コンテナのタイムゾーンが正しくホストに追従するようになれば、`steering-new` スキルの `date +%Y%m%d` はそのままで現地日付を返すため、スキル自体の変更は不要になる可能性が高い。実際に変更が不要かどうかは design.md で確認する。

## 受け入れ条件

- [ ] コンテナ内の `date` コマンドが、ホスト環境の現地タイムゾーンに基づく日時を返す(UTC 固定ではない)
- [ ] 特定のタイムゾーンをハードコードした設定になっていない
- [ ] `steering-new` スキルで作成する `.steering/[YYYYMMDD]-...` の日付が、コンテナの現地日付と一致する
- [ ] コンテナを異なるホストタイムゾーンで起動した場合にも(検証可能な範囲で)同じ仕組みで追従することが説明できる

## 制約事項

- `.devcontainer/**` は Claude が直接編集できない(`permissions.deny` とフックで拒否される)。変更が必要な場合は差分を `proposed/` に作成し、適用はユーザーに依頼する(直近の [`[REMOVED]`]([REMOVED]) と同じ扱い)
- 検証には devcontainer のリビルドが必要になる可能性が高く、このセッション内では完了できない場合がある。その場合は「未実施・検証待ち」として明示する
- `steering-new` スキル(`.claude/skills/steering-new/SKILL.md`)側の変更は、手順1のロジックそのものを作り替えるのではなく、タイムゾーンの前提が変わったことに伴う最小限の追随に留める
