# commit スキルに push まで含めるかどうかのオプションを追加

## 要点

### 採る方式

`--push` という単独のフラグを 1 つだけ追加する。`--no-push` は置かない。

| 指定 | 挙動 |
|---|---|
| (省略) | コミットのみ。push しない |
| `--push` | コミット後、現在のブランチの upstream へ `git push` する |
| `--branch` + `--push` | エラー。何もせず報告して終了する |

push は `git push`(引数なし)だけを使い、`-u` / `origin HEAD` などの upstream 補完を一切行わない。upstream が設定されていないブランチでは push を試みずに報告して終える。**「upstream をどう決めるか」という判断をスキルから完全に取り除く**のが今回の設計の芯であり、`--branch` との排他もこの一点に由来する。

### それを分けた決め手

| 論点 | 採った選択 | 決め手 |
|---|---|---|
| オプションの形 | `--push` のみ | 既定が「push しない」で曖昧さがない。`--here` が必要だったのは「デフォルトブランチにいても確認しない」という既定が読み手に不安を与えるためで、push にはその構図がない |
| `--branch` との排他の実装位置 | 手順1(現状確認)の冒頭 | 要件は「コミットもブランチ作成も行わない」。`git add -A` を含む手順2より前に置かないと、ステージだけ進んだ状態で止まる |
| upstream 未設定時 | 事前に検出し、push を試みない | `git push` に任せると失敗するだけだが、その前に確認ダイアログ(`Bash(git push*)` は `ask`)が 1 回出る。失敗が確定している操作で承認を求めないほうがよい。検出に使う `git rev-parse --abbrev-ref @{upstream}` は読み取りで承認が不要 |
| push 失敗時 | コミットを残したまま報告 | コミットは既に成立している。`git reset` での巻き戻しは復旧手段のない操作として `deny` 対象でもあり、スキルが自動で行う筋合いがない |

### 採らなかった選択肢

- **`--no-push` を対で置く** — `--here` と同じ「既定を明示するだけのフラグ」だが、push の既定は誰も誤解しない。引数表が 1 行伸びるだけで得るものがない
- **`--push` に `--branch` を許し、`git push -u origin <新ブランチ名>` を発行する** — 要件どおり不採用。upstream 名(`origin` 固定でよいか)とリモート命名の前提をスキルが抱え込むことになる
- **upstream 未設定時に `git push -u origin HEAD` へフォールバックする** — 排他にした理由がそのまま当てはまる。リモート名の決め打ちが入る
- **push の確認をスキル自身が行う** — `Bash(git push*)` が `permissions.ask` にあり、Claude Code が確認ダイアログを出す。二重に確認する意味がない

## 実装アプローチ

### 1. 引数の追加(`SKILL.md` 冒頭)

frontmatter の `argument-hint` を更新する。

```yaml
argument-hint: '[--branch[=名前] | --here] [--push] [コミットメッセージのタイトル(省略可)]'
```

引数の表に 1 行追加する。

| 指定 | 意味 |
|---|---|
| `--push` | コミット後に `git push` する。`--branch` とは併用できない |

表の直後に排他の説明を置く。

- `--branch` と `--push` は併用できない。新規作成したブランチには upstream がなく、push には `-u` とリモート名の指定が要る。スキルがリモートの命名を前提に持たないため、この組み合わせは受け付けない
- ブランチを切ったうえで push したい場合は、`--branch` でコミットしたあとユーザーが `git push -u origin <ブランチ名>` を実行する
- `--here` と `--push` は併用できる(`--here` は既定の明示であり、push の要否とは軸が異なる)

使用例に 2 行追加する。

```text
/commit --push
/commit --push docs: READMEの導入手順を修正
```

### 2. 排他チェック(手順1)

手順1(現状確認)の先頭に、引数の妥当性確認を置く。

- `--branch` / `--branch=<名前>` と `--push` が同時に指定されている場合、**以降の手順に進まない**。ステージもコミットもブランチ作成も行わず、併用できない旨と回避手順(`--branch` でコミット後に手動 push)を報告して終了する

### 3. 引数の除去(手順3)

タイトル決定時に取り除くオプションの列挙へ `--push` を加える。

```markdown
- `$ARGUMENTS` から `--branch` / `--branch=<名前>` / `--here` / `--push` を取り除く
```

### 4. push 手順の新設(手順6)

現行の手順5(コミット)にある `- **push はしない。** 明示的に指示された場合のみ行う` を削除し、新しい手順6として push を独立させる。現行の手順6(報告)は手順7へ繰り下がる。

```markdown
6. **push**(`--push` が指定されている場合のみ)
   - `git rev-parse --abbrev-ref @{upstream}` で現在のブランチの upstream を確認する
   - upstream がない場合は push を試みず、その旨と `git push -u <リモート> <ブランチ>` が必要である旨を報告する
   - upstream がある場合は `git push` を実行する
   - 失敗した場合もコミットは取り消さない。エラー出力をそのまま報告する
```

`--push` が指定されていない場合はこの手順を丸ごと飛ばす(現行と同じく push しない)。

### 5. 報告(手順7)

報告項目に push の結果を加える。

```markdown
- `--push` を指定した場合は push の結果(成否、push 先のリモートとブランチ)を報告する
```

### 6. README の更新

スキル一覧の `commit` 行の説明に、push がオプトインである旨を加える。

### 7. バージョン更新

`plugins/core/.claude-plugin/plugin.json` を `0.2.0` → `0.3.0` にする。スキルの引数が増える機能追加であり、既存の呼び出し方は変わらないため minor。

## 影響範囲の分析

### 動作への影響

- `--push` を付けない従来の呼び出し(`/core:commit`、`/core:commit --branch`、タイトル指定)は挙動が変わらない
- `--push` を付けた場合、`Bash(git push*)` が `ask` である導入先では push のたびに確認ダイアログが出る。`permissions` から外している導入先では無確認で push される。どちらになるかは利用側リポジトリの `.claude/settings.json` 次第であり、スキル側では制御しない
- `--branch --push` はこれまで「`--push` が未知の文字列としてタイトルに混入する」挙動だったが、今後はエラーになる。実質的な後退はない

### 後方互換性

`core` プラグインは `0.x` 系であり、`claude.md` のバージョニング方針では後方互換性を担保しない段階にある。今回は既存の引数の意味を変えず追加のみのため、そもそも破壊的変更にならない。

### 永続的ドキュメントへの影響

- `docs/` はこのリポジトリに存在しないため対象外
- `README.md` のスキル一覧に 1 行分の更新が必要(実装アプローチ 6)
- `claude.md` は権限方針とステアリング運用を扱っており、個別スキルの引数は記載していないため更新不要
