# todoリストの先頭項目をステアリングとして実行するオプションの追加

## 要点

### 採る方式

**既存の `steering-new` スキルに「手順0: 開発タイトルの決定」を追加し、`--todo` 指定時はここで todo ファイルの先頭未完了項目を開発タイトルへ変換してから、既存の手順1〜7へそのまま渡す。** 手順7(実装)の末尾に、対応する todo 項目を `- [x]` にする後処理を追加する。

| 論点 | 方式 | 決め手 |
|---|---|---|
| オプションの実現方法 | 既存スキルへの手順追加(手順0) | `--todo` は「開発タイトルの入力元を変える」だけであり、手順1以降のステアリング運用(段階承認・ファイル構成)は一切変わらない。別スキルにすると承認フローを二重管理することになる |
| 一度に処理する件数 | 先頭の未完了項目 1 件のみ | 要求どおり「先頭を実行する」に絞る。複数件の一括処理は承認ステップの管理が複雑になり、今回のスコープを超える |
| todo 項目をチェック済みにするタイミング | 手順7(実装)完了後 | 手順3・4に承認ステップが残っており、requirements/design が却下される可能性がある。実装完了前にチェックすると「未完了なのに完了扱い」になる |

### 採らなかった選択肢

- **独立した新スキル(例 `/steering-from-todo`)にする** — ステアリングの段階承認ロジックをスキル間で重複させることになる。今回追加したいのは開発タイトルの取得元だけであり、既存スキルへの手順追加で足りる
- **todo ファイルの未完了項目を一括でステアリング化する** — 要求は「先頭のひとつ」。一括処理は「N個目が却下されたら以降どうするか」といった制御が増え、今回のスコープを超える
- **ディレクトリ作成時点(手順1)で todo 項目をチェック済みにする** — 承認前に完了扱いにしてしまう。実装完了後(手順7)に動かすほうが実態に合う

## 実装アプローチ

変更対象は `.claude/skills/steering-new/SKILL.md` のみ。

### 1. フロントマター・引数説明の更新

`argument-hint` を次のように変更する。

```yaml
argument-hint: '[--todo[=<ファイル名>] | 開発タイトル]'
```

冒頭の「引数: `$ARGUMENTS`」の説明に、`--todo` / `--todo=<ファイル名>` の扱いを追記する(`commit` スキルの `--branch` / `--branch=<名前>` と同じ書き方に倣う)。

| 指定 | 意味 |
|---|---|
| (省略、通常のテキスト) | 従来通り、そのテキストを開発タイトルとして扱う |
| `--todo` | リポジトリルートの `todo.md` を対象に、手順0で開発タイトルを決定する |
| `--todo=<ファイル名>` | 指定したファイル(リポジトリルート基準の相対パス)を対象に、手順0で開発タイトルを決定する |

`--todo` はこれ単体、または `--todo=<ファイル名>` の形のみを受け付ける。この後に続けてテキストがある場合(例: `--todo タイトル文字列`)は、開発タイトルの取得元が曖昧になるため、手順0の中でユーザーに意図を確認する(`--todo` を優先しテキストを無視する、ではなく確認を挟む)。

### 2. 手順0: 開発タイトルの決定(新設、手順1の前)

```markdown
0. **開発タイトルの決定**(`--todo` 指定時のみ。通常の呼び出しでは `$ARGUMENTS` をそのまま開発タイトルとして手順1へ進む)
   - `--todo` の後にファイル名がなければ `todo.md`、`--todo=<ファイル名>` なら `<ファイル名>` を対象ファイルとする(リポジトリルート基準)。
   - 対象ファイルを先頭から読み、最初に現れる `- [ ] <テキスト>` 行を採用する。見出し(`## foo` など)による分類は無視し、出現順のみで判定する。
   - 採用した行の `<テキスト>` 部分を、以降の手順で使う開発タイトルとする。**元の行全体(`- [ ] <テキスト>`)を、手順7の後処理で使うために保持しておく。**
   - 対象ファイルが存在しない、または `- [ ] ` 項目が1件も見つからない場合は、ステアリングディレクトリを作成せず、その旨をユーザーに伝えて終了する。
   - `--todo` の後に解釈できないテキストが続く場合は、開発タイトルをどちらから取るかユーザーに確認してから進める。
```

以降、手順1〜6は変更なし(`$ARGUMENTS` を「手順0で決定した開発タイトル」と読み替えるだけ)。

### 3. 手順7(実装)末尾への追記

```markdown
   - `--todo` 経由で開始した場合、実装完了後に対象ファイルを確認し、手順0で保持した行(`- [ ] <テキスト>`)がそのまま残っていれば `- [x] <テキスト>` に書き換える。作業中に対象ファイルの当該行が変更・削除されている場合は書き換えず、その旨をユーザーに報告して手動更新を依頼する。
```

行の一致判定は文字列の完全一致で行う(手順0で保持した行そのものを検索する)。同一テキストの行が複数存在する場合は一意に特定できないため書き換えず、ユーザーに報告する。

## 変更するコンポーネント

| ファイル | 変更内容 |
|---|---|
| `.claude/skills/steering-new/SKILL.md` | `argument-hint` と冒頭の引数説明に `--todo` / `--todo=<ファイル名>` を追加。手順0(開発タイトルの決定)を新設。手順7末尾に todo 項目のチェック更新処理を追加 |

他のスキル(`commit` など)・フック・`README.md` / `README.en.md` は変更しない。

## データ構造の変更

なし。既存の Markdown チェックボックス形式(`- [ ] ` / `- [x] `)をそのまま読み書きするだけで、新しいファイル形式やスキーマは導入しない。

## 影響範囲の分析

### 動作への影響

- 通常の呼び出し(`/steering-new [開発タイトル]`、テキストをそのまま渡す形)は手順0を素通りするため、挙動は変わらない
- `--todo` を使った場合のみ、開発タイトルの決定元が変わり、実装完了後に todo ファイルへの書き込みが 1 箇所増える
- 他のスキル・フック(`commit`、`pretooluse-block-prohibited.sh` など)には影響しない

### 後方互換性

このリポジトリはまだ正式なバージョニングの対象ではなく、`steering-new` スキルも社内的な運用ツールである。今回の変更は既存の呼び出し形式を維持したうえでの追加のため、後方互換性上の懸念はない。

### 永続的ドキュメントへの影響

- `docs/` はこのリポジトリに存在しないため、更新対象なし
- `README.md` / `README.en.md` の `steering-new` に関する記述は「機能追加・修正のためのステアリングディレクトリを作成し、段階承認しながら進める」という要約と、詳細を `claude.md` と `SKILL.md` へ委ねる形になっており、`--todo` オプションの追加後もこの要約と矛盾しない。更新不要
- `claude.md` の `steering-new` への言及も同様に要約レベルであり、矛盾しない。更新不要

### 今回の範囲外

- todo ファイルの複数項目を一括でステアリング化する機能
- `todo.md` の日付・タイムゾーンに関する既知の不具合(requirements.md の制約事項に記載)
- todo ファイルのフォーマット自体(見出し構成など)の変更
