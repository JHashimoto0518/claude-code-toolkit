# docsを生成する

## 要点

### 採る方式

| 対象 | 方式 | 決め手 |
|---|---|---|
| 各ドキュメントの見出し構成 | `claude.md` の「ドキュメントの分類」がファイルごとに既に列挙している見出しをそのまま使う | このリポジトリ自身が `claude.md` の運用ルールに従う立場である以上、独自の見出し構成を新たに考案する理由がない。該当しない見出し(画面遷移図等)は削除せず「該当なし」と明記して残す(見出し構成が `claude.md` の定義と一致していることが分かるように) |
| `README.md` / `claude.md` との整合性の取り方 | `README.md` には `docs/` への案内リンクのみ追加する。`claude.md` は変更しない | `claude.md` は利用側リポジトリに配布される汎用テンプレートであり、`claude-code-toolkit` 自身の固有情報(このリポジトリ独自のドキュメントへのリンクなど)を書き込むと配布物としての汎用性を損なう。`README.md` は既に「ステアリング運用」など個別トピックへの案内リンクを持つ構成のため、そこに `docs/` への案内を足すのが自然 |
| `plugins/core/.claude-plugin/plugin.json` の `version` | 更新しない | `docs/` はこのリポジトリ自身のプロジェクト説明であり、配布物である `plugins/core/` 配下(スキル・フック・権限設定)には含まれない。バージョンは配布するプラグインの変更を表すものであり、今回はプラグインの変更を伴わない |

## 背景

[`../20260816-01-add-workflow-feature/`](../20260816-01-add-workflow-feature/) 以降、`docs/` は「利用側リポジトリが自身のプロダクト用に作るもの」という前提だったが、`claude-code-toolkit` 自体も1つのプロダクト(Claude Code設定の配布ツールキット)であり、その設計・構造・用語を恒久的なドキュメントとして持つことに意味がある。requirements.md で決めた通り、対象は `claude.md` が定義する5種のドキュメントで、既存の `README.md` / `claude.md` との重複・矛盾を避ける。

## 実装アプローチ

### 1. `docs/` 配下5ファイルの新規作成

`claude.md` の「ドキュメントの分類」節が列挙する見出し構成に従い、`claude-code-toolkit` 自身の実態を記載する。CLI/設定配布リポジトリという性質上、該当しない見出み(画面遷移図など)は削除せず、「該当なし」と明記した上でその理由を1行添える(見出み自体を削ると `claude.md` の定義との対応が読み取れなくなるため)。

各ファイルの記載内容の要約:

- **`product-requirements.md`**: プロダクトビジョン(複数リポジトリで共有する Claude Code 設定を一元管理・配布する)、対象ユーザー(複数プロジェクトで Claude Code を使う開発者)、主要機能一覧(`commit`/`steering-new` スキル、3フック、権限設定テンプレート、devcontainer 設定)、機能要件・非機能要件(マーケットプレイス配布、開発中で後方互換性非保証、コンテナ内利用前提など)
- **`functional-design.md`**: スキル(`SKILL.md` + `workflows/*.yaml` によるプロンプト駆動)とフック(`hooks.json` 定義 + シェルスクリプト)のアーキテクチャ、マーケットプレイス→プラグイン→スキル/フックの構成図(Mermaid)、コンポーネント設計(各スキル・フックの役割)。データモデル定義・画面遷移図・ワイヤーフレーム・API設計は「該当なし(DBを持たない/GUIを持たないCLI配布リポジトリのため)」と明記
- **`architecture.md`**: 技術スタック(Bash / JSON / YAML / Markdown / Devcontainer / Claude Code プラグイン機構)、開発ツールと手法(devcontainer, git, マーケットプレイス機構)、技術的制約(`claude.md` の「開発環境の権限設定」「開発環境」節への参照。bubblewrap 不可のため sandbox 無効、など)。パフォーマンス要件は「該当なし」と明記
- **`repository-structure.md`**: トップレベル構成(`.claude-plugin/` / `plugins/core/` / `.claude/` / `.devcontainer/` / `.steering/` / `docs/`)のツリーと役割、新しいドメイン特化プラグインを追加する場合の配置ルール(`plugins/<name>/` を `core` の兄弟として追加)
- **`glossary.md`**: マーケットプレイス・プラグイン・スキル・フック・ステアリング・ワークフロー(`kind`/`gate`)などこのリポジトリ固有の用語の定義と英日対応表

### 2. `README.md` への案内リンク追加

「ステアリング運用」節と同様の体裁で、`docs/` 配下の5ファイルへの案内(見出しと1行説明)を追加する。既存の「含まれるもの」節などの内容は変更しない。

## 変更するコンポーネント

- `docs/product-requirements.md`(新規)
- `docs/functional-design.md`(新規)
- `docs/architecture.md`(新規)
- `docs/repository-structure.md`(新規)
- `docs/glossary.md`(新規)
- `README.md`(`docs/` への案内リンクを追加)

## データ構造の変更

コードのデータ構造変更はない。各ドキュメントの見出し構成(`claude.md` の定義に対応)は次の通り。

| ファイル | 見出し構成(`claude.md` 定義) | 本リポジトリでの扱い |
|---|---|---|
| `product-requirements.md` | プロダクトビジョンと目的 / ターゲットユーザーと課題・ニーズ / 主要な機能一覧 / 機能要件 / 非機能要件 | すべて記載 |
| `functional-design.md` | 機能ごとのアーキテクチャ / システム構成図 / データモデル定義(ER図含む)/ コンポーネント設計 / ユースケース図・画面遷移図・ワイヤーフレーム / API設計 | データモデル定義・画面遷移図・ワイヤーフレーム・API設計は「該当なし」と明記。他は記載 |
| `architecture.md` | テクノロジースタック / 開発ツールと手法 / 技術的制約と要件 / パフォーマンス要件 | パフォーマンス要件は「該当なし」と明記。他は記載 |
| `repository-structure.md` | フォルダ・ファイル構成 / ディレクトリの役割 / ファイル配置ルール | すべて記載 |
| `glossary.md` | ドメイン用語の定義 / ビジネス用語の定義 / UI/UX用語の定義 / 英語・日本語対応表 / コード上の命名規則 | UI/UX用語の定義は「該当なし」と明記。他は記載 |

## 影響範囲の分析

- 対象は `docs/` 配下の新規ファイルと `README.md` の追記のみ。`claude.md` および `plugins/` 配下のスキル・フック実装は変更しない
- ドキュメントの新規作成のみで挙動の変更を伴わないため、後方互換性への影響はない。`plugins/core/.claude-plugin/plugin.json` の `version` も対象外(理由は「要点」参照)
- `docs/` 新設により `plugins/core/hooks/posttooluse-doc-check.sh`(コード変更時に `docs/*.md` の記載陳腐化を助言するフック)が実際にチェック対象を持つことになる。フック自体の変更は不要(既に `docs/*.md` を対象にしている)だが、今後 `plugins/` 配下のコードを変更する際にこのフックが `docs/` の該当箇所を指摘する可能性がある点は影響として認識しておく
