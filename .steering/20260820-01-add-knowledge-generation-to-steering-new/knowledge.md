# steering-newスキルへのknowledge生成の追加

### 対人コミュニケーションの文章を扱う際の評価軸

- **学んだこと**: 「Claudeの出力とユーザーが手を加えた結果を比較して意図を読み取る」という要求を一般化する際、比較対象の**置き場所**(リポジトリ外のファイルか、ステアリングディレクトリ内に格納されたファイルか)の一般化と、学びの**種類**の一般化は分けて考える必要があった。CSV/Excelの例(技術的なデータ)を基準に「意図」「文体」「ニュアンス」という語で一括りにしてしまったが、ユーザーが本当に伝えたかったのは「対人コミュニケーションの文章(チャットメッセージなど)をClaudeが作成する場合は、内容の正しさだけでなく、読み手の感情や理解のしやすさに配慮してほしい」という、技術文書とは異なる評価軸だった。
- **根拠**: 会話中の訂正によるもの(成果物の差分比較ではない)。overview.md に例2(校正済みチャット文章)が追記された段階では「文体・ニュアンス」という表現で requirements.md に反映したが、その後ユーザーから「例2を追加した意図は、技術文書ではなく、チャットのような対人のコミュニケーションメッセージをあなたに作ってもらう場合は、正しさだけでなく、読み手の感情や理解容易性に配慮してほしい、ということです」という直接のフィードバックを受け、requirements.md の該当箇所(要点・背景・機能説明・受け入れ条件)を修正した。
- **以降のステアリングで踏まえるべき点**:
  - 「意図の差分を読み取る」系の要求を一般化するときは、比較対象の置き場所の一般化(機械的に一般化しやすい)と、学びの評価軸の一般化(成果物の性質によって質的に異なりうる)を分けて考える。ユーザーが挙げた個別の例から早期に単一の語彙へ抽象化しすぎず、各例が指す評価軸の違いをいったん明示してから一般化したほうが手戻りが少ない。
  - Claudeが対人コミュニケーション用の文章(チャットメッセージ、通知文、ユーザー向けの説明文など)を作成・修正するタスクでは、内容の正しさに加えて、読み手の感情・理解のしやすさへの配慮を評価軸として明示的に意識する。

### plugin.json のバージョン管理運用

- **学んだこと**: `plugins/core/.claude-plugin/plugin.json` の `version` を Minor バージョンアップする作業を、design.md / tasklist.md 作成時点で漏らしていた。過去の類似ステアリング(`20260816-01-add-workflow-feature`)では新機能追加の実装コミットにバージョンアップが含まれていたにもかかわらず、design.md の「変更するコンポーネント」に `plugin.json` を挙げていなかった。
- **根拠**: ユーザーからの「pluginのバージョンは上げないのですか?」という質問による指摘。`git log`(`a497e2c`)を確認して初めて、このリポジトリでは新機能追加の実装コミットに `plugin.json` の Minor バージョンアップが伴う運用だと気づいた。
- **以降のステアリングで踏まえるべき点**: `steering-new` スキルで新機能を追加する design.md を書く際は、「変更するコンポーネント」に `plugins/core/.claude-plugin/plugin.json` の Minor バージョンアップも既定で含めるか検討する。過去の実装コミット(`git log -- plugins/core/.claude-plugin/plugin.json`)を確認すれば、新機能追加時にバージョンを上げる運用であることが分かる。
