このリポジトリのコミット規約に従って、現在の変更をコミットします。

引数: `$ARGUMENTS`

空でよい。オプションとコミットメッセージのタイトルを組み合わせて指定できる。オプションは先頭・末尾のどちらに書いてもよく、**オプションを取り除いた残りをタイトルとして扱う**。

| 指定 | 意味 |
|---|---|
| (省略) | 現在のブランチにそのままコミットする。**確認は求めない** |
| `--here` | 上と同じ。既定の挙動であることを明示したいときに使う |
| `--branch` | 作業ブランチを新規作成してからコミットする。ブランチ名は自動で決める(下記) |
| `--branch=<名前>` | 指定した名前で作業ブランチを新規作成してからコミットする |
| `--push` | コミット後に `git push` する。`--branch` とは併用できない |
| 上記以外の文字列 | コミットメッセージのタイトルとして使い、規約からの自動判定を上書きする |

`--branch` と `--push` は併用できない。新規作成したブランチには upstream がなく、push には `-u` とリモート名の指定が要る。このスキルはリモートの命名を前提に持たないため、この組み合わせは受け付けない。ブランチを切ったうえで push したい場合は、`--branch` でコミットしたあとユーザーが `git push -u origin <ブランチ名>` を実行する。

`--here` と `--push` は併用できる(`--here` は既定の明示であり、push の要否とは軸が異なる)。

`--branch` でブランチ名を省略した場合の決め方:

- 変更に `.steering/[YYYYMMDD]-[NN]-[開発タイトル]/` の新規追加が含まれる場合は、そのディレクトリ名をそのままブランチ名にする(例: `20250115-01-add-tag-feature`)
- 含まれない場合は、変更内容から英語 kebab-case の短い名前を組み立てる

既定でブランチを切らず確認も求めないのは、この運用を採るリポジトリでは `git log` 上コミットがデフォルトブランチへ直接積まれているため。ブランチを分けたいときだけ `--branch` を渡す。手順1で確認した `git log` がブランチ運用を示している場合は、そちらに合わせる。

使用例:

```text
/commit
/commit --branch
/commit --branch=fix-login-redirect
/commit fix: ログイン後のリダイレクト先が誤っていた
/commit --branch improve: エラーメッセージを具体化
/commit --push
/commit --push docs: READMEの導入手順を修正
```

## コミット規約

### タイトル形式

```text
<prefix>: <要約>
```

`prefix` は次のいずれかを使う(このリポジトリの既存履歴で使われているもの)。

| prefix | 用途 |
|---|---|
| `change` | 既存の挙動・仕様を変更する |
| `add` | 新しいファイル・機能を追加する |
| `fix` | 不具合を修正する |
| `refactor` | 挙動を変えずに構造を整理する |
| `improve` | 挙動を変えずに品質・コスト・可読性を改善する |
| `docs` | ドキュメントのみの変更 |
| `chore` | 設定・ツール・雑務 |

### ステアリングを伴う変更のタイトル

`.steering/[YYYYMMDD]-[NN]-[開発タイトル]/` を作成して進めた作業をコミットする場合、要約には**ステアリングディレクトリ名をそのまま**使う。

```text
change: 20250115-01-add-tag-feature
```

- 日付と連番を含むディレクトリ名を丸ごと使う。日付や連番を落としたり、内容を要約し直したりしない
- 連番のない旧形式のディレクトリ(例: `change: 20250110-add-tag-feature`)が残っているリポジトリでは、その場合もディレクトリ名をそのまま使う
- prefix は原則 `change`。ただし作業の性質が明らかに `add` / `fix` の場合はそちらを使ってよい
- 1 つのステアリングディレクトリ = 1 コミットを基本とする

### 本文

タイトルだけで意図が伝わらない場合は本文を書く。ステアリングを伴う変更では原則として書く(タイトルがディレクトリ名だけになり、内容が読み取れないため)。

- 1 行目に「何をどう変えたか」を 1〜2 文で書く
- 続けて主要な変更点を箇条書きにする
- 設計上の判断(採用しなかった選択肢とその理由など)があれば末尾に 1 行添える
- ステアリングの `requirements.md` / `design.md` を丸写ししない。読み手がコミット単位で把握できる粒度に絞る

### CHANGELOG.md の更新

`.steering/[YYYYMMDD]-[NN]-[開発タイトル]/` の新規追加を伴うコミットでは、`CHANGELOG.md` の `## [Unreleased]` に変更内容を追記する。ステアリングを伴わないコミットでは追記しない。

- `CHANGELOG.md` がまだ存在しない場合は新規作成する。ファイル先頭に `# Changelog` の見出しと、[Keep a Changelog](https://keepachangelog.com/) を参考にしている旨・エントリの対象が `.steering/` を経由した変更のみである旨を1〜2文で書いた説明を置き、その下に `## [Unreleased]` を用意してから追記する。`.claude/changelog-version-command` が存在する場合は、バージョンの区切りがそのコマンドの出力に対応する旨も説明に加える
- 追記する文言は、本文の1行目(「何をどう変えたか」の要約)を使う
- prefix からカテゴリへの対応:

  | prefix | カテゴリ |
  |---|---|
  | `add` | Added |
  | `fix` | Fixed |
  | `change` / `refactor` / `improve` / `docs` / `chore` | Changed |

  変更の主眼が既存ファイル・機能の削除である場合は、prefix によらず `Removed` を使ってよい
- 該当カテゴリの見出しがなければ新設する
- リポジトリごとにバージョンの管理方法が異なるため、バージョン番号は決め打ちにせず `.claude/changelog-version-command` で外出しする(`.claude/test-command` と同じ考え方)
  - `.claude/changelog-version-command` が存在する場合: そのコマンドを実行して現在のバージョン文字列を取得する。`CHANGELOG.md` に既にある最新の `## [x.y.z]` 見出しと異なる場合、`## [Unreleased]`(今回追記分を含む)を `## [<取得したバージョン>] - <今日の日付>` に差し替えて確定し、ファイル先頭に新しい空の `## [Unreleased]` を追加する
  - `.claude/changelog-version-command` が存在しない場合: バージョンによる区切りは行わず、常に `## [Unreleased]` に追記し続ける

## 手順

1. **現状確認**
   - `$ARGUMENTS` に `--branch` / `--branch=<名前>` と `--push` が同時に指定されていないか確認する。同時指定の場合は**以降の手順に進まない**。ステージもコミットもブランチ作成も行わず、併用できない旨と回避手順(`--branch` でコミットしたあと `git push -u origin <ブランチ名>` を実行する)を報告して終了する
   - `git status --short` と `git branch --show-current` を実行する
   - `git log --oneline -5` で直近のコミットメッセージ形式を確認する(規約が更新されている可能性があるため、履歴の実態を優先する)

2. **コミット対象の確認**
   - 変更内容を `git diff` / `git diff --staged` で確認する
   - **生成物や一時ファイルが混ざっていないか確認する。** ビルド成果物・配布アーカイブ・言語処理系のキャッシュディレクトリ・検証用に退避したファイル(元のファイル名にハッシュや日付を付けたもの)など
   - `.gitignore` 対象外だが本来コミットすべきでないファイルがある場合、ステージせずユーザーに報告する
   - 意図しないファイルがなければ `git add -A` でステージする

3. **タイトルの決定**
   - `$ARGUMENTS` から `--branch` / `--branch=<名前>` / `--here` / `--push` を取り除く
   - 残りがあればそれをタイトルとして使う
   - 残りがなければ規約に従って組み立てる
     - 変更に `.steering/[YYYYMMDD]-[NN]-[開発タイトル]/` の新規追加が含まれる場合、そのディレクトリ名を要約に使う
     - 複数のステアリングディレクトリが含まれる場合は、コミットを分けるべきかユーザーに確認する
     - ステアリングを伴わない場合は、変更内容から prefix と要約を決める

4. **CHANGELOG.md の更新**
   - 変更に `.steering/[YYYYMMDD]-[NN]-[開発タイトル]/` の新規追加が含まれない場合、この手順は何もせず次に進む
   - 含まれる場合、「CHANGELOG.md の更新」の規約に従って `CHANGELOG.md` を編集し、`git add CHANGELOG.md` でステージする

5. **ブランチの決定**
   - `--branch` / `--branch=<名前>` が指定されている場合のみ、`git switch -c <名前>` で作業ブランチを作成する。名前の決め方は冒頭の引数の説明に従う
   - 指定がない場合(および `--here` の場合)は、現在のブランチのままコミットする。**デフォルトブランチにいてもユーザーに確認しない**
   - 同名のブランチが既に存在して作成に失敗した場合は、コミットせずユーザーに報告する

6. **コミット**
   - ヒアドキュメント(`git commit -F -`)でメッセージを渡す。`-m` の連結は使わない

7. **push**(`--push` が指定されている場合のみ。指定がなければこの手順を飛ばす)
   - `git rev-parse --abbrev-ref @{upstream}` で現在のブランチの upstream を確認する
   - upstream がない場合は push を試みず、その旨と `git push -u <リモート> <ブランチ>` が必要である旨を報告する
   - upstream がある場合は `git push` を実行する。`-u` やリモート名・ブランチ名の補完はしない
   - 失敗した場合もコミットは取り消さない。エラー出力をそのまま報告する

8. **報告**
   - コミットハッシュとタイトル、変更ファイル数・行数を報告する
   - 作業ブランチを作成した場合は、そのブランチ名も報告する
   - `--push` を指定した場合は push の結果(成否、push 先のリモートとブランチ)を報告する
   - `.gitignore` により除外された生成物があれば、その旨を添える
   - `CHANGELOG.md` を更新した場合は、その旨も添える

## 注意事項

- **`Co-Authored-By` などの共同作者トレーラーを付けない。** 生成ツールの利用を示す記述(ツール名・モデル名・自動生成を示す絵文字や定型句)もメッセージに含めない。既定でこれらを付ける挙動があっても、このリポジトリでは抑止する
- コミット前に、ユーザーが承認していない変更が含まれていないか確認する。ステアリング運用中の場合、design.md と永続的ドキュメント更新の承認を経ていない実装が混ざっていないかを見る(tasklist.md 自体は承認ステップではない)
- `.claude/test-command` があるリポジトリでは、コミット前にそのコマンドを実行しグリーンであることを確認する。失敗している場合はコミットせず報告する
- 規約とこのファイルの記述が食い違う場合は、`git log` で観測される実際の運用を優先し、その旨をユーザーに伝える
