あなたはこのリポジトリの `CLAUDE.md` に定義されたステアリング運用に従って、新しい作業単位のドキュメントを作成します。

引数: `$ARGUMENTS`

| 指定 | 意味 |
|---|---|
| 通常のテキスト | 開発タイトルとして扱う。ユーザー自身が指定したものであり、何を作るのかを内容から推測し直さない。誤字や句読点などの体裁は「kind: overview」の範囲で整えてよい。日本語で指定された場合のみ、ディレクトリ名にする際に英語の kebab-case へ翻訳する。既に英語 kebab-case 相当であればそのまま使う |
| `--todo` | 開発タイトルを手入力する代わりに、リポジトリルートの `todo.md` の先頭の未完了項目を開発タイトルとして使う。詳細は手順0を参照 |
| `--todo=<ファイル名>` | 上と同じだが、対象ファイルを `todo.md` の代わりに `<ファイル名>`(リポジトリルート基準の相対パス)にする |
| `--workflow=<id>` | 使用するワークフローを指定する。`<id>` は `plugins/core/skills/steering-new/workflows/<id>.yaml` のファイル名(拡張子除く)に対応する。省略時は `standard`(通常の開発)を使う。`--todo` / 開発タイトルとは独立して指定でき、順序は問わない。詳細は手順1を参照 |

## 手順

0. **開発タイトルの決定**(`--todo` 指定時のみ。通常のテキストが渡された場合はこの手順を飛ばし、そのテキストを開発タイトルとして手順1へ進む)
   - `--todo` の後にファイル名がなければ `todo.md`、`--todo=<ファイル名>` なら `<ファイル名>` を対象ファイルとする(リポジトリルート基準)。
   - 対象ファイルを先頭から読み、最初に現れる `- [ ] <テキスト>` 行を採用する。見出し(`## foo` など)による分類は無視し、出現順のみで判定する。
   - 採用した行の `<テキスト>` 部分を、以降の手順で使う開発タイトルとする。**元の行全体(`- [ ] <テキスト>`)は、`kind: implementation` の後処理で使うために保持しておく。**
   - 対象ファイルが存在しない、または `- [ ] ` 項目が1件も見つからない場合は、ステアリングディレクトリを作成せず、その旨をユーザーに伝えて終了する。
   - `--todo` の後に解釈できないテキストが続く場合(例: `--todo タイトル文字列`)は、開発タイトルの取得元が曖昧なため、どちらを使うかユーザーに確認してから進める。

1. **ワークフローの決定**
   - `$ARGUMENTS` から `--workflow=<id>` を取り除く(取り除き方は `--todo` と同様、位置は問わない)。指定がなければ `id = standard` とする。
   - `plugins/core/skills/steering-new/workflows/<id>.yaml` を Read する(このスキルのベースディレクトリからの相対パス)。
   - 該当ファイルが存在しない場合は、`workflows/` 配下に存在するファイル名(拡張子を除いたもの)の一覧を提示し、どれを使うかユーザーに確認してから進める。ディレクトリはまだ作成しない。
   - 読み込んだ YAML の `steps` 配列を、以降の手順(手順3)で先頭から順に実行する。各要素は `kind`(手順種別)・`file`(作成するファイル。省略される場合もある)・`gate`(ゲート種別)を持つ。`kind` の意味は「手順種別(kind)の定義」を、`gate` の意味は「ゲート種別」を参照する。

2. **ディレクトリ作成**
   - `$ARGUMENTS` が空の場合、開発タイトルをユーザーに質問してから開始する(日本語・英語どちらでもよい旨を伝える)。
   - 開発タイトルが日本語の場合は英語の kebab-case に翻訳し、ディレクトリ名に使う(例: 「タグ機能の追加」→ `add-tag-feature`)。既存の `.steering/*` のタイトルと同程度の粒度・命名感に合わせる。既に英語 kebab-case であればそのまま使う。
   - 今日の日付を `YYYYMMDD` 形式で取得し、`.steering/[YYYYMMDD]-[NN]-[開発タイトル]/` を作成する(例: `.steering/20250115-01-add-tag-feature/`)。
   - `NN` は**同日内の連番**(`01` から始まる 2 桁のゼロ埋め)。同じ日付で始まるディレクトリの件数 + 1 を使う。同日に既存がなければ `01`。件数は次で確認する(`20250115` は今日の日付に読み替える)。

     ```bash
     ls -1 .steering/ | grep -c '^20250115-'
     ```

     - 連番を付ける理由: 日付だけだと同日に複数作成したときディレクトリ名のソート順が作成順と一致せず、経緯を追う際に前後関係を誤読する。
     - 連番のない旧形式(`[YYYYMMDD]-[開発タイトル]`)のディレクトリが残っているリポジトリでは、過去分をリネームしない(過去のコミットタイトルが旧名を埋め込んでおり、リネームすると対応が失われるため)。同日に旧形式がある場合もそれを件数に含めて次の番号を決める。
   - 既に同名ディレクトリが存在する場合は、上書きせずユーザーに確認する。

3. **ワークフローの実行**
   - 手順1で読み込んだ `steps` を先頭から順に実行する。各要素について、`kind` に対応する内容(「手順種別(kind)の定義」)に従ってファイルを作成・更新し、`gate` に対応する待機挙動(「ゲート種別」)に従って次の要素に進むかどうかを判断する。
   - あるステップの `gate` を通過していない状態で次のステップに進まない。

## ゲート種別

| gate | 挙動 |
|---|---|
| `none` | そのまま次のステップへ進む |
| `user_input` | テンプレート・下書きを作成し、ユーザーが記入・確認して進行を指示するまで待つ。ユーザーが無言で他の話題に移った場合は進めるべきか確認する。指示を受けたら、その時点のファイル内容を読み込み、以降のステップの入力として扱う |
| `approval` | 内容を提示し、ユーザーの明示的な承認を得るまで次に進まない。内容に触れず先の作業を促しただけの返答は承認とみなさず、意思を確認する |
| `approval_if_needed` | 影響の有無をまず判断する。影響がある場合は該当内容(diff相当)を提示し `approval` と同様に承認を待つ。影響がない場合はその旨を明示し、待たずに次へ進む |

## 手順種別(kind)の定義

### kind: overview(背景・要求の概要)

- `file` に指定されたファイル(通常 `overview.md`)を作成する。H1 見出しには `$ARGUMENTS` で指定された開発タイトルを、**文書の見出しとして読める体裁に整えて**入れる。`## 目的` 以降は次の軽量なテンプレートのみとし、具体的な内容はまだ埋めない(ユーザー自身が後で編集するため):
  ```markdown
  # [開発タイトル]

  ## 目的

  (ここに背景・要求の概要を記載してください)

  ## 注意事項

  (制約条件や注意点があれば記載してください)
  ```
- H1 に入れるのは日本語なら日本語のままであり、ディレクトリ名用の英語 kebab-case ではない(例: ディレクトリが `20250115-01-add-tag-feature/` でも、H1 は日本語で書く)。
- **整えてよいもの**(気づいたら直す):
  - 誤字・脱字・変換ミス
  - 不適切または不足している句読点、読みにくい語順
  - リポジトリ内の正式表記との不一致(識別子・関数名・ファイル名などはコード上の正確な表記に合わせる)
  - 見出しとして必要な用語の補完(例: 「`notify_user` を呼び出したい」→「`notify_user` 関数を呼び出す」)
  - 依頼口調の語尾(「〜したい」「〜してほしい」)を、見出しらしい体言止め・断定形へ調整する
- **変えてはいけないもの**:
  - 開発の意図・目的・対象スコープ。言い回しの調整に留め、別の要求に読み替えない
  - ユーザーが明示した情報の削除。短くするために要素を落とさない
  - 指定されていない前提・手段の追加(「非同期で」「バッチで」など、ユーザーが書いていない実現方法を勝手に足さない)
- 判断に迷う場合はユーザーの指定表現を尊重する。原文から大きく変えた場合は、H1 をどう整えたかを作成報告時に一言添え、ユーザーが直せるようにする。
- `gate: none` の場合(例: `minor-fix`)は、ユーザーへの確認を挟まず、`$ARGUMENTS` の内容をもとに Claude が概要を要約して `## 目的` 以降を埋め、そのまま次のステップに進む。
- `## 目的` 以降(背景・要求の概要)を Claude が代わりに書いたり推測で埋めたりするのは、`gate: none` が明示されている場合に限る。それ以外(`gate: user_input`)では H1 のタイトルとテンプレートのみを作成する。

### kind: requirements(requirements.md の作成)

- `file`(通常 `requirements.md`)の内容を読解した上で作成する(前のステップで作成したファイルの文面をそのまま複製・引用するのではなく、通常どおり読解して反映する)。
- 既存の `.steering/*/requirements.md` の構成(背景 / 変更・追加する機能の説明 / 受け入れ条件 / 制約事項)に倣う。
- **H1 の直後に `## 要点` を置く**(後述の「「要点」セクション」を参照)。ここには「何をどう変えるか」と「今の方式のどこを捨てるか」を書く。
- 背景セクションは、必要に応じて過去のステアリングディレクトリ(`../[既存ディレクトリ]/`)への相対リンクで経緯を示す。

### kind: design(design.md の作成)

- 既存の `.steering/*/design.md` の構成(実装アプローチ / 変更するコンポーネント / データ構造の変更 / 影響範囲の分析)に倣う。
- **H1 の直後に `## 要点` を置く**(後述の「「要点」セクション」を参照)。ここには「どの方式を採るか」と「それを分けた決め手」を書く。
- 「影響範囲の分析」には後方互換性への影響を含める。配慮の要否はリポジトリのバージョニング方針に従う(`CLAUDE.md` の「バージョニングと後方互換性ポリシー」を参照)。本番未リリースであれば、壊す変更を自由に行ってよい。

### kind: docs_update(永続的ドキュメント(`docs/`)の更新)

- 直前までの内容をもとに、`docs/` 配下(`architecture.md` / `functional-design.md` / `product-requirements.md` / `repository-structure.md` / `glossary.md` など)・`README.md`・各種 `*_GUIDE.md` のうち影響を受ける箇所を特定する。
- 影響がある場合: 該当ファイルを実装より先に更新し、変更内容(diff相当)をユーザーに提示する(`gate: approval_if_needed` の待機挙動に従う)。
- 影響がない場合: その旨を明示する。
- **このステップでは実装ファイル(アプリケーションコード・インフラ定義など)を一切変更しない。** ドキュメント更新と実装を同一ステップで進めない。

### kind: tasklist(tasklist.md の作成)

- 既存の `.steering/*/tasklist.md` の構成(実装 / インフラ / テスト / ドキュメント更新 / 未実施・検証待ち、など該当するセクションのみ)に倣い、チェックボックス形式(`- [ ]`)で列挙する。
- 直前に `kind: docs_update` があった場合、`docs/` 更新はそこで完了済みのため、tasklist.md の「ドキュメント更新」セクションには steering ディレクトリ内の記録のみを残すか、完了済みとして扱う(未着手のタスクとして再掲しない)。
- 実環境へのデプロイなど、このセッションで検証できない項目は「未実施・検証待ち」として明示する。

### kind: implementation(実装)

- `.steering/[YYYYMMDD]-[NN]-[開発タイトル]/tasklist.md` があれば、それを実装のタスクリストとして扱う旨を伝えてから着手する。tasklist.md がないワークフロー(`gate: none` の単一ステップ構成など)では `$ARGUMENTS` および直前のステップで作成した内容を実装範囲として扱う。
- 実装はタスクリスト(またはそれに相当する合意範囲)を超えない。設計上決めた内容を超える変更が必要になった場合は、その場で進めず一度ユーザーに報告する。
- tasklist.md がある場合、完了した項目はチェックボックスを `- [x]` に更新する。このセッションで検証できない項目は `- [ ]` のまま「未実施・検証待ち」に残す。
- `--todo` 経由で開始した場合、実装完了後に対象ファイルを確認し、手順0で保持した行(`- [ ] <テキスト>`)がそのまま残っていれば `- [x] <テキスト>` に書き換える。作業中に対象ファイルの当該行が変更・削除されている場合、または同一テキストの行が複数存在し一意に特定できない場合は書き換えず、その旨をユーザーに報告して手動更新を依頼する。

### kind: exploration_summary(探索的な壁打ちの要約)

- ユーザーと対話しながら、開発タイトルに関するテーマを掘り下げる(要件を先に確定させるのではなく、選択肢や論点を一緒に洗い出す)。
- 対話の区切りごとに `file`(通常 `overview.md`)へ内容を反映する。H1 見出しの扱いは `kind: overview` と同じ(開発タイトルをそのまま体裁を整えて使う)。
- `requirements.md` / `design.md` / `tasklist.md` は作成しない。ユーザーが「進める」「終わり」など区切りの意思を示すまで対話・更新を続ける(`gate: user_input` の待機挙動)。

### kind: investigation_report(調査結果の報告)

- 開発タイトルに関する調査(コード・ドキュメントの調査、外部情報の確認など)を行う。
- 結果を `file`(通常 `overview.md`)に、背景 / 調査結果 / (あれば)今後の論点、のようにまとめる。H1 見出しの扱いは `kind: overview` と同じ。
- `requirements.md` / `design.md` / `tasklist.md` は作成しない。実装ファイルの変更も行わない。

## 「要点」セクション

`requirements.md` と `design.md`(`kind: requirements` / `kind: design` が作成するファイル)は、H1 の直後に `## 要点` を置く。本文を最後まで読まなくても**その文書で何が決まったのかが分かる**ようにするためのもの。

- **位置**: H1 の直後。「背景」「実装アプローチ」など他のどのセクションよりも前に置く
- **対象**: `kind: requirements` / `kind: design` が作成するファイルのみ。`overview.md` は要求そのものが短くユーザーが書くため、`tasklist.md` はチェックリスト自体が要約になっているため、いずれも置かない
- **内容**: 結論を先に書く。requirements なら「何をどう変えるか」と「今の方式のどこを捨てるか」、design なら「どの方式を採るか」と「それを分けた決め手」。採らなかった選択肢がある場合は、その理由を 1 行添える
- **分量**: 数段落、または短い `###` 見出しで区切った数ブロック。スクロールせずに読み切れる範囲に収める
- **書き方**:
  - 判断とその決め手だけを書く。本文の各セクションを順に要約した目次にしない
  - 仕様の対応関係(カラムと意味、担い手と理由など)が中心になる場合は表を使う。散文で並べるより短く済む
  - 本文と内容が重なることを避けなくてよい。要点は本文の抜粋ではなく、本文を読む前提として先に渡す結論である
- 書き方に迷ったら、そのリポジトリの `.steering/` にある直近の `requirements.md` / `design.md` を参考にする。

## 実装開始の条件

- `kind: implementation` のステップに到達する前のすべてのステップの `gate` を通過していること。標準ワークフロー(`standard`)であれば、docs更新(`kind: docs_update`)の承認を得ており、かつ tasklist.md(`kind: tasklist`)を作成済みであること。
- `kind: tasklist` 自体は `gate: none` であり承認は不要。それより前の段階承認で設計は確定しており、tasklist.md はそれを作業単位に分解した記録に過ぎないため、ここで承認を挟む意味がない。

## 注意事項

- このコマンドが呼ばれた時点でステアリングドキュメントの作成要否はユーザーが判断済みである。作成するかどうかを自分で判断し直したり、ユーザーに確認したりしない。
- `kind: requirements` と `kind: design` のステップをまとめて一度に提示しない。1ファイルごとに作成し、`gate` の待機挙動に従ってから次のステップに進む。
- `kind: requirements` / `kind: design` が作成するファイルには必ず `## 要点` を置く。分量が少ないという理由で省略しない(短い文書ほど要点も短くなるだけ)。
- **ステップの順序は 手順0(開発タイトル決定)→ 手順1(ワークフロー決定)→ 手順2(ディレクトリ作成)→ 手順3(ワークフロー実行: ワークフロー YAML の `steps` を順に実行)で固定する。** 各ワークフロー内での `kind` の順序も、YAML に列挙された順から変えない。
- `gate: approval` / `gate: approval_if_needed` / `gate: user_input` のいずれかを持つステップでは、明示的な指示・承認の返答を得るまで次のステップの作業に着手しない。ユーザーが無言で他の話題に移った、または内容に触れず先の作業を促しただけの場合は承認とみなさず、意思を確認する。
- `gate: none` のステップは承認ステップではない。完了したらそのまま次のステップに進む。
- 開発タイトルは `$ARGUMENTS` としてユーザー自身が指定する。何を作るのかを内容から推測し直したり、別のスコープに要約し直したりしない。ディレクトリ名には英語 kebab-case へ翻訳した形を、`overview.md` の H1 には日本語のまま体裁を整えた形を使う(`kind: overview` を参照)。
